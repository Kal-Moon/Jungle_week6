1. 이번 주에 공부한 개념

1-1. 동적 메모리 할당기란

  • 프로그램이 실행 중에 "메모리 좀 줘"(malloc), "다 썼어"(free) 하는 요청을 처리하는 프로그램이다.
  • 할당기가 관리하는 영역은 힙(heap) 이다. 힙은 가상 주소 공간에서 데이터 영역 바로 위에 있고, 위쪽(높은 주소)으로 자란다. 힙의 끝은 커널이 brk 포인터로 관리한다.
  • 힙을 늘리는 시스템 콜이 sbrk다. Malloc Lab에서는 memlib.c의 mem_sbrk가 이것을 흉내 낸다(미리 잡아 둔 큰 배열을 조금씩 내어 준다).
  • 할당기는 두 가지를 동시에 잘해야 한다. 둘은 서로 부딪친다.
    • 처리량(throughput): 1초에 몇 개의 요청을 처리하는가 → mdriver의 Kops
    • 메모리 이용도(utilization): 힙 크기 중 실제로 쓰이는 비율 → mdriver의 util
  • mdriver 점수 계산: Perf index = 60 × util + 40 × min(1, 처리량 / 기준 처리량)
    • 그래서 util은 60점, thru는 40점 만점이다. 평균 util이 4%p 올라도 점수는 약 2~3점밖에 오르지 않는다(실험에서 직접 체감함).

배경: 가상 메모리와 힙의 관계

  • 프로세스는 각자 0번지부터 시작하는 자기만의 가상 주소 공간을 쓰고, 실제 물리 메모리와는 페이지 단위로 연결된다(페이지 테이블).
  • sbrk로 힙을 늘리는 것은 "가상 주소 범위를 넓히는 것"이다. 실제 물리 페이지는 처음 접근할 때 페이지 폴트를 거쳐 연결된다.
  • malloc은 이렇게 받아 온 큰 덩어리를 잘게 쪼개서 나눠 주는 역할이다. 매번 커널에 부탁하면 느리기 때문이다(CHUNKSIZE = 4KB씩 한 번에 늘림).

1-2. 단편화 (Fragmentation)

종류 뜻 이번 주 코드에서 생기는 곳
내부 단편화 나눠 준 블록 안에서 낭비되는 공간 헤더·풋터(8바이트), 8바이트 정렬을 위한 패딩, 최소 블록 크기(16바이트)
외부 단편화 빈 공간의 합은 충분한데, 한 덩어리로 붙어 있지 않아 못 쓰는 상태 binary 트레이스: 작은 칸·큰 칸을 번갈아 받고 한쪽만 반납 → 빈칸 사이에 사용 중인 칸이 끼어 합쳐지지 못함

binary, binary2 트레이스의 util이 어떤 방식을 써도 55%, 51%에서 움직이지 않은 이유가 바로 외부 단편화다. "어느 칸을 고르느냐"로는 해결되지 않는다.

1-3. 블록 구조와 경계 태그 (Boundary Tag)

bp-4      bp                             bp+size-8
|         |                              |
v         v                              v
+---------+------------------------------+---------+
| header  | payload (+ padding)          | footer  |
| size|a  |                              | size|a  |
+---------+------------------------------+---------+
  • 헤더: 블록 크기 + 할당 여부(맨 아래 1비트)를 한 워드(4바이트)에 함께 저장한다.
    • 블록 크기는 항상 8의 배수라 아래 3비트가 늘 0이다. 그 빈 비트에 할당 여부를 넣는다.
    • 그래서 GET_SIZE는 & ~0x7(아래 3비트 지우기), GET_ALLOC은 & 0x1(맨 아래 비트만 보기)이다.
  • 풋터: 헤더의 복사본을 블록 끝에 둔다. 이게 경계 태그다. 덕분에 바로 앞 블록의 크기를 알 수 있고(앞 블록의 풋터 = 내 헤더 바로 앞), 앞 블록과 합치는 일을 상수 시간에 할 수 있다.
  • bp(block pointer)는 헤더가 아니라 payload의 시작을 가리킨다. 사용자에게 돌려주는 주소가 이것이다.
매크로 하는 일
PACK(size, alloc) 크기와 할당 비트를 한 워드로 합치기
GET(p) / PUT(p, val) 주소 p에서 한 워드 읽기 / 쓰기
HDRP(bp) / FTRP(bp) 이 블록의 헤더 / 풋터 위치
NEXT_BLKP(bp) / PREV_BLKP(bp) 메모리상 바로 다음 / 이전 블록의 bp

1-4. 힙의 시작 모양: 프롤로그와 에필로그

+---------+-----------+-----------+-----------+
| pad 0   | 8/1 hdr   | 8/1 ftr   | 0/1 hdr   |
+---------+-----------+-----------+-----------+
  padding |<------ prologue ----->| epilogue
                      ^
                      heap_listp
  • 프롤로그(크기 8, 할당됨)와 에필로그(크기 0, 할당됨)는 가짜 블록이다.
  • 힙의 맨 앞과 맨 끝에 "항상 할당된 칸"을 세워 두면, coalesce에서 "앞 칸이 없을 때", "뒤 칸이 없을 때"를 따로 처리하지 않아도 된다.
  • 에필로그의 크기가 0이라서, 힙을 순회할 때 GET_SIZE(HDRP(bp)) > 0이 "아직 끝이 아니다"라는 조건이 된다.

1-5. 요청 크기 맞추기 (asize)

if (size <= DSIZE)
    asize = 2*DSIZE;                                    /* 최소 블록 16바이트 */
else
    asize = DSIZE * ((size + (DSIZE) + (DSIZE-1)) / DSIZE); /* 헤더+풋터 8 더하고 8의 배수로 올림 */
  • 사용자가 1바이트를 달라고 해도 헤더 4 + 풋터 4 + 정렬 때문에 16바이트 블록이 된다(내부 단편화).

1-6. 빈 블록 찾기 정책 (Placement Policy)

정책 방법 장점 단점
first fit 처음부터 보다가 맞는 첫 칸 단순, 큰 칸이 뒤쪽에 남음 앞쪽에 작은 조각이 쌓여 점점 느려짐
next fit 지난번에 멈춘 자리부터 앞쪽 조각을 건너뛰어 빠름 조각이 힙 전체에 퍼져 util이 떨어지기 쉬움
best fit 끝까지 다 보고 가장 딱 맞는 칸 util이 가장 좋음 매번 끝까지 봐야 해서 느림

1-7. 분할 (Splitting)과 연결 (Coalescing)

분할(place): 찾은 칸이 필요한 것보다 충분히 크면(남는 부분이 최소 블록 16바이트 이상) 둘로 나눈다. 앞은 할당, 뒤는 빈칸.

연결(coalesce): 블록을 반납할 때 앞뒤 칸이 비어 있으면 합친다. 경계 태그 덕분에 4가지 경우를 상수 시간에 처리한다.

Case 앞 칸 뒤 칸 결과
1 할당 할당 그대로
2 할당 빈칸 나 + 뒤
3 빈칸 할당 앞 + 나 (bp가 앞 칸으로 이동)
4 빈칸 빈칸 앞 + 나 + 뒤 (bp가 앞 칸으로 이동)

이번 구현은 반납하자마자 합치는 즉시 연결(immediate coalescing) 이다.

1-8. 빈 블록을 관리하는 세 가지 방법

방법 구조 찾는 시간
implicit free list 모든 블록(할당 + 빈칸)을 크기로 건너가며 순회 전체 블록 수에 비례
explicit free list 빈칸끼리만 이중 연결 리스트로 연결 빈칸 수에 비례
segregated free list 크기별로 리스트를 여러 개 둠 해당 크기 리스트만 보면 됨

explicit free list에서 빈칸의 모양:

+--------+-----------+-----------+-------+--------+
| header | PRED      | SUCC      |  ...  | footer |
| size|0 | prev free | next free |       | size|0 |
+--------+-----------+-----------+-------+--------+
         ^           ^
         bp          bp+4
  • 빈칸은 어차피 payload를 안 쓰니까, 그 자리에 "줄에서 앞 빈칸 주소", "뒤 빈칸 주소"를 적는다. 추가 메모리가 들지 않는다.
  • 32비트에서는 주소가 4바이트라 헤더 4 + PRED 4 + SUCC 4 + 풋터 4 = 16으로 최소 블록 크기가 implicit과 같다. 64비트라면 포인터가 8바이트라 최소 블록이 더 커진다.
  • 반납된 칸을 줄 어디에 넣을지:
    • LIFO: 맨 앞에 넣기. 넣기가 O(1). 이번 주 구현 방식.
    • 주소 순서: 주소 순으로 정렬해 넣기. 넣기는 느리지만 util이 더 좋다고 알려져 있다.

1-9. realloc

  • 처음 받은 naive 버전: 새로 malloc → 내용 memcpy → 옛 블록 free.
  • 이번 주 결과에서 가장 큰 병목이었다. 전체 실행 시간 0.222초 중 0.200초를 realloc 트레이스 하나가 쓴다.
  • 개선 방향(다음 주 이후 과제): 바로 뒤 칸이 비어 있거나 힙의 끝이면 제자리에서 늘리기, 크기가 줄어드는 경우는 그대로 돌려주기.

1-10. 이번 주에 새로 알게 된 C 개념

개념 정리
포인터 연산의 단위 (char *)로 바꾸고 더해야 "바이트 단위"로 움직인다. 매크로마다 (char *)(bp)가 있는 이유
위치 vs 크기 주소는 주소끼리, 크기는 크기끼리 비교해야 한다. 섞으면 comparison between pointer and integer
매크로는 쓰일 때 컴파일된다 틀린 매크로를 정의만 해 두면 에러가 안 난다. 쓰는 순간 터진다
매크로 결과는 상자가 아니다 NEXT_BLKP(bp) = NULL;은 불가능(lvalue required). 계산 결과는 =의 왼쪽에 못 온다
함수 호출 모양 remove_free;는 이름만 적은 것. remove_free(bp);처럼 괄호와 인자가 있어야 호출
변수 vs 함수 변수에는 괄호를 붙이지 않는다. 함수 이름을 변수 자리에 넣으면 함수 코드의 주소가 들어간다
for (시작; 조건; 이동) 세 칸이 모두 필요하다. 가운데를 지우면 컴파일러가 이동식을 조건으로 읽는다
statement with no effect copySize - DSIZE;처럼 계산만 하고 결과를 버리는 줄
경고 없음 ≠ 정답 부등호 방향이 반대인 조건은 컴파일은 되지만 조용히 아무 일도 안 한다

2-1. implicit free list 기본 함수 (#14~#19)

책의 구조를 따라 매크로 → mm_init → extend_heap → mm_free → coalesce → mm_malloc 순서로 작성했다. mm_malloc이 아직 없는 place를 불러서 링크 에러(undefined reference to 'place')로 실행은 못 했다.

2-2. first fit과 place (#20, #23)

for (bp = heap_listp; GET_SIZE(HDRP(bp)) > 0; bp = NEXT_BLKP(bp)) {
    if (!GET_ALLOC(HDRP(bp)) && GET_SIZE(HDRP(bp)) >= asize) {
        return bp;
    }
}
return NULL;
  • 처음에는 크기만 비교해서 이미 할당된 칸도 고를 수 있었다. !GET_ALLOC(...)을 추가해서 해결.
  • 첫 실행: 11개 중 9개 통과. realloc, realloc2는 mm_realloc did not preserve the data from old block.

2-3. mm_realloc 수정 (#24)

naive 코드는 블록 크기를 SIZE_T_SIZE(8바이트) 앞에서 읽었다. 그런데 우리 블록의 크기는 4바이트 앞의 헤더에 있다. 8바이트 앞은 앞 블록의 풋터다.

copySize = GET_SIZE(HDRP(ptr));   /* 헤더에서 블록 크기를 읽고 */
copySize = copySize - DSIZE;      /* 헤더+풋터 8바이트를 뺀 것이 payload 크기 */

다섯 번 고친 끝에 11/11 통과, 첫 점수 53점(util 44 + thru 8).

2-4. next fit (#21)

목표: thru가 8점밖에 안 나와서, 매번 처음부터 찾지 말고 지난번에 멈춘 자리(find_heap)부터 찾게 한다.

해결해야 했던 문제 두 가지 - 문제 A: 멈춘 자리부터 끝까지만 찾고 포기 → 앞쪽 빈칸을 다시 못 써서 힙만 늘어남(Ran out of memory). 처음부터 find_heap 직전까지 한 번 더 찾는 두 번째 for 문으로 해결. - 문제 B: 기억해 둔 칸이 coalesce로 앞 칸과 합쳐지면 find_heap이 큰 칸의 한가운데를 가리킴 → Payload overlaps another payload. 합친 뒤 find_heap이 그 칸 안쪽에 있으면 칸의 시작으로 옮겨서 해결.

/* coalesce 끝 */
if (find_heap > (char *)bp && find_heap < NEXT_BLKP(bp)) {
    find_heap = bp;
}

결과: thru 8 → 30~34점, 74~78점. binary 트레이스는 10~25배 빨라졌다. 대신 util은 74% → 73%로 조금 떨어졌다.

2-5. 명시적 가용 리스트 (#22, mm-explicit.c)

mm.c(next fit 버전)는 그대로 두고, 복사본 mm-explicit.c에 따로 구현했다.

추가/수정 내용
매크로 PRED, SUCC 빈칸 안에서 앞/뒤 빈칸 주소가 적힌 자리 (bp, bp + 4)
전역 변수 free_listp 빈칸 줄의 맨 앞. 처음에는 NULL
insert_free 줄의 맨 앞에 넣기 (LIFO)
remove_free 줄에서 빼기 (앞 칸과 뒤 칸을 서로 이어 줌)
coalesce 합칠 이웃은 줄에서 빼고, 합친 결과를 줄에 넣기
place 할당할 칸은 줄에서 빼고, 쪼개고 남은 조각은 줄에 넣기
find_fit 옆 칸이 아니라 줄의 뒤 칸으로 이동

세 방식의 find_fit 비교 (for 문 세 칸만 다르다)

방식 시작 계속할 조건 다음으로 이동
first fit (implicit) heap_listp 크기가 0이 아닌 동안 옆 칸 NEXT_BLKP(bp)
next fit (implicit) find_heap 크기가 0이 아닌 동안 옆 칸 NEXT_BLKP(bp)
explicit (LIFO, first fit) free_listp NULL이 아닌 동안 줄의 뒤 칸 (char *)GET(SUCC(bp))

결과: 76~82점. coalescing을 뺀 0~8번 트레이스가 next fit보다 약 3~12배 빨라졌다(coalescing만 오히려 조금 느려짐).

first fit 42 29~40 71~82
best fit 45 18 63
next fit 43 16~18 59~61
  • best fit이 진 이유: util은 4%p 올랐지만 점수로는 3점. 대신 binary 트레이스에서 합쳐지지 못한 빈칸 수천 개를 요청마다 끝까지 훑느라 thru가 16~22점 떨어졌다. 정작 binary의 util은 그대로였다.
  • next fit이 진 이유: LIFO에서는 쪼개고 남은 조각이 줄의 맨 앞에 들어간다. 기억해 둔 자리는 이미 줄 중간이라 쓸 만한 칸이 늘 등 뒤에 있고, 거의 한 바퀴를 돌아야 찾는다. LIFO + first fit은 이미 "가장 최근 빈칸부터 보기"를 하고 있어서 next fit이 할 일을 대신하고 있었다.

결과에서 읽은 것

  1. 찾기 속도는 해결됐고, 이제 병목은 realloc이다. explicit로 0~8번은 크게 빨라졌는데 전체 처리량은 next fit과 비슷하다. 9번(realloc) 트레이스가 전체 시간의 약 90%를 쓴다.
  2. util은 방식을 바꿀수록 조금씩 떨어졌다. next fit과 LIFO 모두 "주소 순서와 상관없이" 빈칸을 고르기 때문에 조각이 퍼진다.
  3. binary 트레이스의 util은 찾기 방식으로 못 고친다. 외부 단편화의 원인이 "고르는 방법"이 아니라 "합칠 수 없는 배치"에 있다.
  4. Kops는 실행할 때마다 다르다. 같은 코드도 thru가 30~34점, 34~40점처럼 흔들린다. 비교할 때는 여러 번 돌려야 한다.

4-2. 조건식의 방향

coalesce 후 find_heap을 바로잡는 조건에서 네 번 시도했다.

  1. find_heap < bp && > NEXT_BLKP(bp) → && 뒤에 왼쪽이 빠짐 (컴파일 에러)
  2. find_heap < !GET_ALLOC(HDRP(bp)) && ... → 0/1과 주소를 비교 (항상 거짓)
  3. find_heap < (char *)bp && find_heap > NEXT_BLKP(bp) → 경고 없이 컴파일 성공, 하지만 결과 그대로
  4. find_heap > (char *)bp && find_heap < NEXT_BLKP(bp) → 성공

3번이 제일 무서웠다. 에러도 경고도 없는데 if 안이 한 번도 실행되지 않았다. "bp보다 앞이면서 다음 칸보다 뒤"인 위치는 존재하지 않기 때문이다. 해결 방법: 숫자를 직접 넣어 확인했다. bp = 100, find_heap = 150, 다음 칸 = 200이면 150은 100보다 크고 200보다 작아야 한다.

4-3. 명시적 리스트: 넣기와 빼기를 함께 맞춰야 한다

  • place만 먼저 고치고 실행했더니 segmentation fault. coalesce가 아직 빈칸을 줄에 넣지 않으니, 줄에 들어간 적 없는 칸을 빼려다 죽은 것이다. 넣는 곳(3곳)과 빼는 곳(5곳)이 모두 맞아야 처음 동작한다.
  • place에서 remove_free(bp)를 bp = NEXT_BLKP(bp); 뒤에 두면, 그때의 bp는 이미 남은 조각이다. 원래 칸을 빼야 하니 함수 맨 위에서 뺀다.
  • coalesce에서 NEXT_BLKP, PREV_BLKP를 지워야 하는지 고민했다 → 지우지 않는다. 합치기는 메모리상 붙어 있는 칸끼리만 하는 일이라 옆 칸 매크로가 그대로 필요하다. 줄의 앞/뒤(PRED, SUCC)는 찾기용이다.
  • remove_free는 네 번 시도했지만 끝내 혼자 완성하지 못하고 코드를 안내받았다. insert_free도 안내받은 코드다. 이중 연결 리스트에서 "앞 칸의 뒤"와 "뒤 칸의 앞"을 동시에 고치는 그림이 머릿속에 잘 그려지지 않았다. 다음 주에 종이에 칸을 그려 가며 다시 직접 써 볼 부분.

4-5. 작업 습관에서 막힌 것

  • 저장 안 하고 make — 두 번이나 "고쳤는데 결과가 그대로"였다. 원인은 에디터에서 저장을 안 한 것. make 전에 Ctrl+S, 이상하면 파일 저장 시각부터 확인.
  • 매크로는 써야 검사된다 — 틀린 pred, sicc 매크로를 정의만 했을 때는 11/11 통과가 나와서 맞는 줄 알았다. 매크로는 쓰이는 순간에야 컴파일된다.
  • 통과 ≠ 정답 — next fit 중간 단계에서 일부 트레이스만 통과한 적이 있는데, 문제 B가 우연히 드러나지 않았을 뿐이었다.

5. 회고 (KPT)

Keep

  • 함수 단위로 이슈를 나누고, 하나 끝날 때마다 커밋 + 기록을 남긴 것. 덕분에 점수 변화와 실패 원인을 날짜별로 되짚을 수 있었다.
  • 실패한 시도를 지우지 않고 ATTEMPTS.md에 남긴 것. 같은 실수(함수 이름을 변수처럼 쓰기, 위치와 크기 비교)가 반복되는 걸 눈으로 확인할 수 있었다.
  • 답을 바로 받지 않고 힌트로 직접 고쳐 본 것. 시간은 오래 걸렸지만 next fit과 coalesce 조건은 끝까지 내 손으로 맞혔다.
  • "best fit이 더 좋지 않나?"를 그냥 믿지 않고 측정해 본 것.

Problem

  • 포인터에서 "위치 / 크기 / 그 자리에 적힌 값"을 계속 섞어 썼다.
  • insert_free, remove_free, find_fit for 문 한 줄 등은 결국 안내받았다.
  • mm_realloc은 naive 버전에서 크기 읽는 부분만 고쳐서, 가장 큰 병목을 아직 손대지 못했다.
  • 코드를 고치기 전에 숫자를 넣어 확인하는 습관이 부족했다(조건식 방향을 네 번 시도함).

Try

  • 포인터 코드를 쓰기 전에 종이에 칸을 그리고 주소 숫자를 직접 넣어 본다.
  • 안내받은 insert_free, remove_free를 빈 파일에서 다시 직접 써 본다.
  • mm_realloc 개선: 뒤 칸이 비었거나 힙 끝이면 제자리에서 늘리기.
  • segregated free list로 찾을 범위를 좁혀서 util과 thru를 같이 올려 보기.
  • ptr == NULL, size == 0일 때의 realloc 처리 추가.
